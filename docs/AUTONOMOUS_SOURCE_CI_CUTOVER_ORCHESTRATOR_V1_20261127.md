# MicroGen_AI_Web — persistent autonomous verified-code promotion and next-task selection

## Why this is required
The existing Dell-115 read-only v7.1 offline development daemon can dispatch evidence-only G2/G3 preparation. PR660/PR661 added a separate persistent Selenium code writer that creates a single authentic Gemini browser request for a **source-pinned**, independently tested code job. However, it previously stopped after successful pytest and waited for ChatGPT to create a GitHub PR, supervise Windows CI and deploy a new main revision. It also had no catalog-backed next-task selection after the original three jobs.

## Code-level corrections
- **Independent job selection:** development_source_pinned_next_job_v1.py verifies a finite exact-SHA original approved catalog and immutable original test specimens. It opens a new local Git worktree from clean GitHub main, commits the original independent pytest test BEFORE any model request, and admits one unique new JSON job into the existing one-Send Selenium worker inbox. A previously consumed/quarantined G3 caption job is never reused. Next-task catalogs must be extended through a new code-reviewed protected PR; this is intentionally not permission for arbitrary AI-generated unsafe instructions.
- **Verified candidate promotion:** development_verified_candidate_promotion_v1.py accepts only a genuine original model response SHA, candidate source SHA, independently executed pytest exit 0, no-paid-API and no-publication flags. It revalidates a restrictive Python AST, copies the original source plus unchanged tests into a fresh isolated worktree from current GitHub main, reruns the independent tests, creates a deterministic Git branch and GitHub PR, waits for both exact-head Windows CI jobs, and calls the existing tested protected REST compare-and-swap merge gate. Write-ahead receipts claim EACH push, PR creation and merge **before** attempting the remote side effect. Restart reconciliation checks exact remote source SHA and PR identity; an uncertain result is NEVER blindly replayed. A failed CI run quarantines that PR lane while other independently eligible development can continue.
- **Guarded deployment:** development_certified_candidate_deploy_v1.py re-checks that GitHub's actual merged main has the **identical tested source tree** and matches the exact PR head. It stages a clean main checkout, uses source-verified original protective PowerShell scripts as immutable templates, preserves the old v7.1 executor and state, and invokes the existing bounded guarded-cutover recovery. Independently verifies BOTH the original read-only Windows daemon and the separate source-code author by native task policy, live PID, command line and fresh heartbeat. A deployment or reboot with uncertain Windows task owner is held, not repeated.
- **Long-horizon supervisor:** development_autonomous_code_loop_v1.py always takes the certified current source root from the original running Windows task. It first closes an eligible merged PR's guarded deployment, then advances at most one source-tested PR (or waits for CI), and finally selects one new approved original code task. A failed job is quarantined without stopping other eligible tasks. The controller never sends model prompts or paid API traffic.
- **Persistent Windows task:** scripts/install_microgen_autonomous_code_promotion_v1.ps1 creates a separate interactive Limited, at-logon, restartable task MicroGen_AI_Web_v1_CodePromotionOrchestrator. It retains both earlier Dell workers. The stable launcher resolves the current production revision before each cycle, so completed guarded cutovers do not strand future code development on an old source checkout.

## What constitutes success
1. Fault-injection tests for original model response drift, changed test SHA, duplicate job, spoofed GitHub main, ambiguous push/PR/merge, CI pending vs failed and both Windows guarded-cutover rollback/restart boundaries.
2. A genuinely new source job admitted automatically by the Windows controller; separate Selenium writer starts a real original model request, saves original reply and authentic independent pytest.
3. If the candidate passes, the new Windows controller creates its GitHub PR, waits for BOTH Windows CI checks, merges with exact-head source proof, safely updates BOTH Windows tasks and immediately selects the next eligible catalog task **without ChatGPT prompting**.
4. Original source checkpoint, requests, cost and publication invariants remain intact; successes and held lanes persist across PC restarts.

Until step 3 is observed on a genuinely new eligible accepted candidate, the integration is implemented and unit-tested but not yet proven fully unattended end-to-end. Preserve this distinction in status reporting.
