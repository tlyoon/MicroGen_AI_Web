# PR366: Durable real-provider TTS retry journal resume after Windows interruption

**Observed §8.5 source-grounded Gemini TTS outage on Dell-115, 29 October 2026:** source figures/slides/narration/script QA have passed and all original source PDFs preserved. Original Flash-Lite Kore generated only slide 1 while slides 2/3 had 125-second timeouts in each of three actual provider queue rounds. Before the repair, a restart of the TTS command would start three new Lite rounds, re-spending credits despite a hash-linked ledger of genuinely failed provider calls. The final queue round also invoked expensive sentence-aware chunking even after adjacent slide failures clearly indicated a global outage. The genuine original run entered its approved full-batch Flash/Kore fallback after three source-bound Lite failures, preserving the original slide 1 candidate.

**Fix:** `selenium_pipeline/tts.py` now reads the existing append-only `AttemptEvidence` records under the *same* source/voice/script identity at startup. If one unresolved slide has already exhausted at least three genuinely observed transient provider calls, a new invocation skips redundant Lite calls and goes directly to the pre-existing verified full-batch Flash/Kore fallback gate. It never constructs fictitious failure events for untried slides, never silently reuses unverified or mixed-provider WAVs, never ignores a permanent error, and refuses a recorded successful call without an identical hash-verified candidate. A prior two-failure slide attempts only the remaining third call on restart. Speech chunking is disabled on the last round when another slide already failed in the same round, so provider outages cannot multiply costly chunk attempts. Cloud fallback still requires *both* truly exhausted Lite and Flash observed histories, and remains single-voice full-batch only. No Whisper, no changed academic TTS tolerance, no publication.
